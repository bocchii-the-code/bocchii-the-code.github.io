[+] AGENTS.md best practices

A complete, battle-tested AGENTS.md for governing autonomous coding agents. Drop this file into any project's root to apply the same workflow discipline to subagents and tool usage.

AGENTS.md

This document governs the behavior, workflow, and technical execution for all autonomous coding agents and subagents operating within this system. Read these instructions carefully before beginning any task.

1. Skill Calling (Tool Usage)

You are equipped with a variety of skills to interact with the codebase, terminal, and external resources. When task-specific prompts are provided (e.g. "Create slides", "read the PDF file"), skim your skill base and call the corresponding skills. Use them judiciously and effectively.

Basic instructions:

  • ALWAYS USE PARALLEL TOOLS WHEN APPLICABLE.
  • Skills live under ~/.config/opencode/skills/.
  • When designing a webpage, report, or slides — anything with visual requirements — use ~/.config/opencode/design-md/ to fetch a style spec, then follow the chosen folder's DESIGN.md strictly. Readability is non-negotiable.

Rules for skill calling:

  • Assess before acting: read files and search code to understand the existing architecture, dependencies, and patterns first.
  • Atomic actions: keep tool calls focused. Do not attempt to modify 10 files in a single edit. Make incremental changes.
  • Verify inputs: ensure file paths and syntax are exactly correct before any code-edit or file-write skill.
  • Handle errors gracefully: if a skill call fails, do not panic. Read the error, analyze the cause, and apply a systematic fix.

2. Subagent Delegation (Orchestration)

Complex tasks must not be handled by a single monolithic process. Break large features into isolated sub-tasks and delegate to specialized subagents.

Delegation workflow:

  1. Analyze the objective — deconstruct the user's prompt into a checklist of sub-tasks.
  2. Define the bounded context — give the subagent the exact context it needs, no more, no less. Specific file paths and clear acceptance criteria.
  3. Dispatch subagents — call the appropriate subagent sequentially or in parallel, depending on the task.
  4. Review and integrate — verify the subagent's work. Ensure it aligns with the task requirements before moving on.

3. Mandatory Post-Update Validation (Smoke Testing)

Reliability is the highest priority. Never assume your code works simply because it looks correct.

CRITICAL RULE: Following any "Large Update," you are strictly required to run the project's smoke tests to verify system stability before reporting the task as complete.

What counts as a Large Update?

  • Changes affecting core architecture, state management, or routing.
  • Modifications spanning 3 or more files.
  • Adding, removing, or upgrading dependencies in package.json (or equivalent).
  • Refactoring existing, functioning components.

The Smoke Test Protocol:

  1. Run the linter / compiler — no syntax errors or strict type warnings.
  2. Execute the smoke test suite — run the designated command via terminal.
  3. Verify application startup — start the local dev server and wait for the signal of successful service startup to ensure the app doesn't crash on boot.
  4. Iterate on failure — if a smoke test fails, halt progress, read the test logs, identify the regression, and fix it. Do not mark the task as complete until tests pass.

4. Standard Execution Loop

For every prompt that involves code implementation, follow this strict loop:

  1. PLAN — analyze the request, explore the codebase, and formulate a step-by-step plan. If the prompt is fuzzy, invoke the grill-me skill to drill down for clarifications.
  2. DELEGATE — break the plan into sub-tasks and assign them to subagents if the scope requires it.
  3. EXECUTE — write code, modify files, implement the features.
  4. TEST — trigger the linter and smoke tests (mandatory for large updates).
  5. REPORT — provide a concise summary of changes, tests run, and final status.
